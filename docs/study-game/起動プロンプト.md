# 新プロジェクト:通年型の勉強ゲーム(仮称)を、AIエージェント会議で企画・制作する

## このセッションの役割

このセッションは、「全国教員支援ポータル」(https://teacher-portal-puce.vercel.app/)に
追加する**通年型の勉強ゲーム専用**のセッションです。
ほかの作業（記事・既存ツールの改良・X運用など)は別のセッションが担当しています。
このセッションではこのゲームのことだけに集中してください。

私は現役の小学校教員で、プログラミングの専門家ではありません。
説明はやさしい日本語で、専門用語を使うときは短い言いかえを添えてください。

作業フォルダ: `C:\Users\andou\OneDrive\デスクトップ\claud code\teacher-portal`

## 背景とねらい

研修で「タブレット依存を防ぐには、規制するのではなく、こちらが学べるゲームを作ればよい」
という話がありました。
これまでの単元ごとのシンプルなツールではなく、**1年間を通して学びながら物語や冒険が進み、
アバターが成長していく「超大作の勉強ゲーム」**を作りたいです。

目指す品質は「スマホアプリのような」ものです。動きが滑らか(目標60fps)で、
押した瞬間に反応し、見た目が楽しく、子どもが自分から開きたくなるものにしてください。

## 最初にやること(作り始める前に)

1. `CLAUDE.md` と `AGENTS.md`、`docs/study-game/` の中のファイル(あれば)を先に読む。
   公開のしかた・承認のルールは `CLAUDE.md` が最優先。
2. 下の「最初に私へ質問してください」を、**選択肢つきで一度にまとめて**聞く。

   区切りの報告のときに番号つきでまとめて聞いてください。

### 最初に私へ質問してください

- 最初に作る対象学年と教科(最初は**1学年・1教科・1学期分**にしぼる前提で)
- 使う端末(iPad / Chromebook / Windowsタブレット)と、学校で使うか・家で使うか
- 1日に遊んでほしい時間の目安
- ゲームの世界観の方向(例:町づくり / 探検 / 乗りもの旅 など、案を3つ出して選ばせる)

## AIエージェント会議

サブエージェントを使い、次の役割で会議を開いてください。**できるだけ同時に走らせ**、
意見がぶつかったところは「どちらを選ぶか」を判断材料つきで私に示してください。

- **ゲームデザイナー**:通年で飽きない物語・ステージ構成、面白さ、成長の気持ちよさ
- **教育内容担当**:学習指導要領に沿った1年間の学習の流れ、問題の種類と難易度、単元とステージの対応
- **学習の専門家**:記憶に残る仕組み(間違えた問題がまた出る、少し難しい問題に挑戦できる、間隔をあけて復習する)
- **アバター・報酬システム担当**:アバターの強化、装備、称号、図鑑など、学ぶほど成長を実感できる仕組み
- **UI・アート担当**:アプリのような見た目と操作感、アニメーション、効果音、低学年でも迷わない画面
- **エンジニア**:実現方法、動作の軽さ、オフライン対応、データの保存方法、ファイル構成
- **安全・健康担当**:依存させない設計と個人情報の保護(下のルールを守らせる役)
- **子ども役**:実際に遊ぶ子どもの立場で「楽しい?」「わかりにくくない?」を本音で言う
- **先生役**:授業や家庭学習でどう使えるか、先生が困らないか

会議の議事録は `docs/study-game/meetings/YYYY-MM-DD-<回>.md` に残してください。

### 会議で決めること

- ゲームの世界観と、4月〜3月の1年間の物語・マップの流れ
- 学習内容とステージの対応。**先生がクラスの進度に合わせてステージを開放できる仕組み**
  (サーバーを使わないので、先生が渡す「かいほうコード」方式などを検討する)
- 問題の形式(選択・入力・並べ替え・図を使う・音を使う)と、難易度の自動調整
- アバターの強化システム、報酬、やり込み要素、図鑑
- 画面一覧と操作の流れ(画面遷移図)
- 技術の方針(例:ホーム画面に追加できてオフラインでも動くWebアプリ〈PWA〉にする、など)
- 最初に作る範囲

## 依存させない設計(必須)

このゲームの出発点は「タブレット依存を防ぐ」ことなので、ゲーム自体が依存を生む作りに
しないでください。

- ガチャ・くじ引き・ランダム報酬・課金要素は入れない
- 「毎日ログインしないと損をする」連続ログイン報酬のような、不安をあおる仕組みは入れない
- 1日のプレイ時間の目安を設け、区切りのよいところで「今日はここまで」と
  気持ちよく終われる工夫を入れる(終わりに今日できるようになったことを見せる)
- 報酬は「遊んだ時間」ではなく「学んだこと・できるようになったこと」に結びつける
- 他の子との順位争いをあおる表示は入れない

## 個人情報・安全ルール(必須)

- 子どもの本名や学校名は入力させない。ニックネームのみ
- 学習データはサーバーに送らず、端末の中だけに保存する(localStorage)。
  端末が変わったときやデータが消えたときのために、サーバーを使わずに続きから遊べる方法
  (昔のゲームの「復活の呪文」のようなセーブコード)を用意する
- アクセス解析・外部広告・外部サイトへのリンク・外部CDNの読み込みを入れない
- キャラクター・画像・音楽はすべてオリジナル。有名ゲームやアニメに似せない。
  効果音は音源ファイルを置かず、Web Audio APIで作る(権利の心配がなく、容量も増えない)
- 問題文は教科書や市販教材を写さず、すべてオリジナルで作る。
  学習内容の正確さは**国立教育政策研究所のサイト(学習指導要領のHTML)**で裏取りする
  (文部科学省のPDFは文字が取り出せないことが多い)
- 運営者(私)を特定できる情報は、ファイル・コメント・コミットに一切書かない

## 技術の決まり(この環境の事情)

- 置き場所: ゲーム本体は `public/study-game/` の中に**複数ファイルに分けて**置く
  (HTML・JS・CSS・問題データのJSON)。
  **1ファイルにまとめない**:このアプリのプレビューは約500KBを超えるHTMLを開けず、
  検証ができなくなる。既存ツールのような単体HTML方式は使わない
- サイトへの登録: `src/lib/tools.ts` に項目を追加して `/tools/<slug>` から開けるようにする
  (`audience: "student"`)。子ども向けページ `/kids` からも入れるようにする
- 問題データは `docs/study-game/questions/` を原本とし、学年・教科・単元ごとのJSONに分ける。
  **あとから問題だけを足せる形**にする(コードを触らずに追加できること)
- 動作確認: `file://` ではJavaScriptが動かない。PowerShellで簡易サーバーを立てて確認する。
  アニメーションの実測(fps)は**プレビューの画面を表示したまま**行う(隠れていると止まる)
- 検証は見た目の確認だけで済ませず、**実測**する:
  初回の読み込み時間、画面の切り替わり、連続タップ、低学年の指でも押せる大きさ(44px以上)
- `npm run lint` と `npm run build` が**エラーなく通ること**を必ず確認してから push する
  (EPERMで落ちたら `.next` を消して再実行)
- 日付を記録するときは Git Bash の `date` を使わない(UTCになる)。
  PowerShell の `Get-Date` を使う
- 同じフォルダで別のセッションが動いていることがある。ブランチやビルドの取り合いを
  避けるため、必要なら scratchpad に `git worktree` を作って作業する
- 公開は `CLAUDE.md` の手順どおり。**`master` に直接 push しない。**
  作業用ブランチ(`feat/study-game-...`)で止め、プレビューURLを私に見せる

## 記録の残し方(最重要)

大きなプロジェクトなので、いつ再開しても続きから進められるよう、
`docs/study-game/` に次を作り、常に最新に保ってください。

- `design.md`:ゲーム設計書(会議で決まったことのすべて)
- `decisions.md`:私が判断したことの記録(日付・内容・理由)
- `progress.md`:進み具合(完了 / 作業中 / 次にやること / 詰まっていること)
- `questions/`:問題データの置き場(学年・教科・単元ごと)
- `meetings/`:会議の議事録

**作業を始めるときは必ず design.md・decisions.md・progress.md を読んでから始め、
終わるときに更新してください。**

## 進め方

1. 私への質問(選択肢つき・一度にまとめて)
2. エージェント会議 → 議事録を残す
3. `design.md` を作り、要点を私に報告する
4. 最初の版は「1学年・1教科・1学期分」程度にしぼり、**最初から最後まで遊べる形で完成**させる
   (全部を同時に作り始めない)
5. 会議 → 実装 → 実測検証を**3巡**くり返して仕上げる(毎回、子ども役と先生役に試させる)
6. 作業用ブランチで止め、プレビューURLを私に見せる。
   私が「公開OK」と言うまで本番サイトには出さない
7. 私の確認とフィードバックを受けて、学期・教科・学年を順に広げていく

## 報告の形式

各段階の終わりに、短くこの形で報告してください。

1. できたこと(**3行以内**)と、確認してほしいプレビューURL
2. 私に決めてほしいこと(**番号つき・選択肢つき**)
3. 次にやること
4. うまくいっていないこと・心配な点(隠さずに正直に)
